DLQ Console Delivery Checklist

Public-safe management summary for a controlled Dead Letter Queue support console. This version intentionally removes organisation-specific hostnames, credentials, tenant identifiers, internal repository paths and environment details.

Shareability note: this page is a desensitised checklist. It describes the delivery approach, control themes and remaining work without exposing infrastructure-specific details.

Objective

Provide a centrally hosted operational console for investigating, importing, querying, replaying and administering DLQ messages in a controlled and audited way.

Target Model

Browser-based frontend, backend API trust boundary, managed database storage, managed secrets and identity-based access control.

Control Position

No local message databases, no frontend-held infrastructure credentials, role-based access, audit records and environment boundary checks.

Key Controls To Preserve

  • Identity-based authentication only.
  • Backend-side authorisation for every action.
  • Separate permissions for read, operate and administer actions.
  • Elevated access for destructive actions.
  • Environment boundaries enforced by the backend.
  • Read-only SQL enforced server-side.
  • Audit successful, failed and denied actions.
  • No payload content in application logs.
  • No infrastructure credentials in the frontend.
  • No local unmanaged message database in the target state.
  • Operational data is not treated as long-term record retention.
  • Internal network exposure only.

Known Validation Risks

RiskPayload Scale
Large payload handling and storage growth need performance validation before broad rollout.
RiskImport Load
Import batch size, throttle values and query timeouts need tuning against real operational volumes.
RiskBroker Versions
Compatibility must be validated against the broker versions and images used in target environments.
RiskAccess Model
Final user-to-database attribution and audit semantics must be agreed before production deployment.
